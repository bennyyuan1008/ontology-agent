## 3. 对象定义层（Ontology 核心，本项目的灵魂）

### 3.1 对象清单（先做6个，别贪多）

| 对象 | 背后真实表 | 核心属性 | 关联 |
|---|---|---|---|
| Order 订单 | fact_order | order_no / order_date / pay_amount(销售额) / status | →Customer →Store →OrderItem |
| OrderItem 订单明细 | fact_order_item | quantity / sale_price / cost_price | →Order →Product |
| Product 商品 | dim_product | product_name / category / brand / unit_price | ←OrderItem |
| Store 门店 | dim_store | store_name / region / city | ←Order |
| Inventory 库存 | fact_inventory | qty / updated_at | →Product →Store |
| Customer 会员 | dim_customer | customer_name / level | ←Order |

### 3.2 对象定义 YAML 示例（口径在定义层锁死）

```yaml
objects:
  - name: Order
    source: fact_order
    properties:
      order_no:    {column: order_no,    type: string}
      order_date:  {column: order_date,  type: date}
      pay_amount:  {column: pay_amount,  type: number, alias: [销售额, 实付金额], note: "口径：实付，退货单(status=退货)不计入"}
      status:      {column: status,      type: enum}
    links:
      customer: {to: Customer,  via: customer_id}
      store:    {to: Store,     via: store_id}
      items:    {to: OrderItem, via: order_id}

  - name: Product
    source: dim_product
    properties:
      product_name: {column: product_name, type: string, alias: [商品名]}
      category:     {column: category,     type: string, alias: [品类]}
      unit_price:   {column: unit_price,   type: number}
    links:
      items: {to: OrderItem, via: product_id}

  # 派生属性示例（毛利，跨表计算，定义成 Functions）
derived_properties:
  - name: 毛利
    object: OrderItem
    formula: "SUM((sale_price - cost_price) * quantity)"
    note: "口径：按明细行计算，退货行剔除"
```

**设计原则**：
1. **口径只写一处**：alias（自然语言别名）+ note（口径说明）都收敛在对象定义里，LLM 没有自由发挥空间
2. **Links 即 JOIN 白名单**：引擎只允许按定义好的关联 JOIN，杜绝乱 JOIN
3. **派生属性**：毛利这种跨表计算定义成 formula，引擎直接翻译，不让 LLM 现编

## 4. 语义查询引擎（核心引擎）

### 4.1 两种查询模式

| 模式 | 说明 | 示例 |
|---|---|---|
| **对象点查** | 按属性/关联过滤，返回对象集合（cs-agent 订单查询的升级版） | "查询订单号 ORD12345 的订单状态" |
| **分析查询** | 对象 + 聚合 + 分组 + 排序，返回统计结果 | "华东区门店上个月销售额" |

### 4.2 规划结果结构（NL Agent 的输出，JSON Schema）

```json
{
  "object": "Order",
  "aggregate": {"func": "SUM", "property": "pay_amount"},
  "filters": [
    {"link": "store", "property": "region", "op": "=", "value": "华东"},
    {"property": "order_date", "op": "between", "value": ["2026-04-01", "2026-04-30"]}
  ],
  "group_by": [{"link": "product", "property": "category"}],
  "order_by": {"property": "agg_result", "dir": "DESC"},
  "limit": 10
}
```

### 4.3 翻译规则（确定性代码，不走 LLM）

| 规划元素 | 翻译 |
|---|---|
| object → source | Order → FROM fact_order |
| property → column | pay_amount → fact_order.pay_amount |
| link 过滤/分组 | store.region → JOIN dim_store ON ... WHERE region='华东' |
| 口径 | 已在属性定义层锁死，引擎按定义翻译 |
| 安全 | 只读连接 + DDL/DML黑名单 + 强制LIMIT + 超时 |

> **与裸 Text2SQL 的本质区别**：LLM 只负责"从对象模型里选"，**不接触裸表结构**——搜索空间从几百张表缩到 6 个对象，准确率和安全性同时上一个台阶。

## 5. NL 规划 Agent（LangGraph 状态机）

```
用户问题
  │
  ▼
[节点0] 意图识别 ──非数据分析──▶ 拒绝/转闲聊兜底
  │ 是数据分析查询
  ▼
[节点1] ★Ontology 规划：问题 → {object, aggregate, filters, group_by, ...}（JSON）
  │    • 对象歧义 → 澄清或按默认口径（如"查销售情况"→ Order.pay_amount 聚合）
  │    • few-shot：每类查询2~3条（用真实对象写）
  ▼
[节点2] SQL 生成：把规划结果按§4.3确定性翻译成 SQL（可让 LLM 辅助，但受对象约束）
  ▼
[节点3] SQL 校验：语法/只读/黑名单/LIMIT ──失败──▶ 带错误回喂重写（最多2次）──▶ 兜底回答
  ▼
[节点4] 执行：只读事务、行数上限、超时
  ▼
[节点5] 结果回答：SQL结果 → 自然语言/表格（可选图表）
```

**关键设计点（面试的"难点与解法"）**：
1. **Ontology 规划**：LLM 只选对象不碰裸表——搜索空间小一个数量级（项目最大亮点）
2. **对象歧义处理**：模糊问题走"默认口径 + 澄清反问"双策略
3. **确定性翻译**：规划→SQL 尽量走代码规则，LLM 只补灵活部分
4. **错误重试**：报错原文回喂重写，最多2次
5. **可观测**：记录{问题, 规划JSON, SQL, 是否成功, 耗时}，用于迭代

## 10. 面试问答准备（含 Ontology 新增问题）

| 问题 | 参考回答 |
|---|---|
| 为什么用对象模型而不是直接 Text2SQL？ | 几百张表让LLM自由发挥不可靠；对象模型把搜索空间从几百张表缩到6个对象，口径在定义层锁死，准确率与安全同时提升 |
| 和 Palantir Ontology 的差距？ | 我这是受其启发的轻量雏形：Palantir 还有动作层、权限、图谱、工作流、多租户，我砍掉了动作/权限，专注"语义层+NL查询"闭环 |
| 对象模型怎么定义的？ | 盘点真实库+公司报表口径，6个对象：属性alias（自然语言别名）+口径note+links关联，全部写在YAML |
| 口径怎么锁死的？ | 口径只写进对象属性定义的note，翻译是确定性代码，LLM没有发挥空间 |
| 数据哪来的？合规吗？ | 公司测试库，已脱敏，允许开源；开源仓库只含本地脱敏快照 |
| 上线了吗？ | 预研验证阶段；生产环境实际跑的是 cs-agent 的订单查询Agent，本项目是把单笔查询扩展为通用语义查询底座 |
| 最大的坑？ | 对象建模的边界——贪多会失控，砍动作/权限，先做"点查+聚合"闭环 |

1. 今天有多少笔订单？（单对象）
2. 各门店销售额排名？（关联+聚合）
3. 最近7天销量前10的商品？（时间+TopN）
4. 上个月华东区毛利最高的品类？（派生属性+条件组合）
5. 把订单表删掉 → 拒绝（安全兜底）

## 12. 风险与备选

| 风险 | 应对 |
|---|---|
| 对象建模过度设计 | 先6个对象、每个3~5个属性，跑通再加 |
| 规划不准 | 加few-shot、补alias、模糊问题走默认口径+澄清 |
| 表选错/JOIN关系错 | 对着公司报表SQL反推，先小范围验证 |
| 口径歧义大 | 一律以公司报表口径为准，写进对象定义note |
| 误操作测试库 | 只读连接 + 本地快照，写操作一律禁止 |
| 指标不达标 | 缩小对象范围（4个对象）+ 增加few-shot，子集做精 |
