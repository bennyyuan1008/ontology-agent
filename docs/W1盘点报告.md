## 2. 技术要点（环境限制与对策）

| 问题 | 现象 | 对策 |
|---|---|---|
| **NCHAR 字符集** | NLS_NCHAR_CHARACTERSET=UTF8(id 871)，python-oracledb **thin 模式读取 NVARCHAR2 列报 DPY-3012** | **CAST 方案**：`CAST(col AS VARCHAR2(n))` 可正常读取（已验证 ✅）；引擎需按列类型自动加 CAST |
| 纯 NUMBER/DATE 列 | 正常读取 ✅ | 无影响 |
| **时间字段是字符串** | DCP_ORDER.STIME='20250819162925132'（YYYYMMDDHH24MISSSSS，17位）；CREATE_DATETIME='...22000'（17位） | 用 `SUBSTR(STIME,1,8)` 得 YYYYMMDD；同格式字符串比较=时间序比较，可行 |
| 数据新鲜度 | REP_SALE_GOODS_DAY 覆盖 **2025-08-19 ~ 2026-08-13**（56家门店）；DCP_ORDER 到 2026-08-12 | 评测集日期可直接用真实区间（如 2026-07） |

## 5. PII 与安全边界（Ontology 天然防线）

以下敏感字段**绝不能进对象模型**（评测集"查询会员手机号→拒绝"用真实案例验证）：

| 表 | 敏感字段 |
|---|---|
| CRM_MEMBER | MOBILEPHONE（手机号）、IDENTITYCODE（身份证）、ADDRESS、EMAIL |
| CRM_CARDMEMBER | MOBILE、IDENTITYCODE |
| DCP_ORG | PHONE、BANKACCOUNT（银行账号）、EMAIL |

> 这正是 Ontology 语义层的价值演示：物理表有敏感字段，但**对象模型不暴露 → LLM 无从查询 → 天然安全**。

## 8. 更新（2026-08-14 晚：报表数据集到货后的关键修正）

**报表数据集**：公司帆软 FineReport 模板库（`.cpt` 为明文 XML，内含报表 SQL）——口径权威来源，已提取并校准。

**重大发现（推翻部分 v1 映射）**：
1. **报表口径主表是 `DCP_SALE`（202万行）而非 `DCP_ORDER`（24.9万行）**！`DCP_SALE_DETAIL` 414万行。对象模型 v2 已重映射：Order→DCP_SALE、OrderItem→DCP_SALE_DETAIL。
2. **口径公式（来自 0104_品类销售汇总.cpt）**：
   - 销售额 = 明细 `AMT` 汇总，**退货单(type=1/2/4)取负相抵**
   - TYPE：0=正常(200.8万) / 1=退货(1.5万) / 2=冲销 / 16=特殊单(排除)
   - 门店过滤 `dcp_org.org_form='2'`；店名 `dcp_org_lang.ORG_NAME(zh_CN)`
   - 品类名 `dcp_category_lang.CATEGORY_NAME`；商品名明细冗余 `PNAME`
3. 存在**两套表体系**（老版 td_*/ta_* 与新版 dcp_*），0101 用 td_sale、0102/0104 用 dcp_sale——以 dcp_* 为准。

**引擎增强**：对象级默认过滤（Store org_form='2'）；子查询属性 `group_key`（品类名按 CATEGORY 分组，绕过 ORA-22818/00979）。

**评测集 v2 已生成**（`04_评测集模板_eval_set_20条.json`）：17条查询真实执行（expected_sql=引擎SQL，expected_result=真实结果=黄金基准）+ 3条拒绝/边界用例。样例：3月销售单 273,878 笔、正常单 271,993、门店第一 直营店1-16 84.7万、退货 8.1万、客单价 33.86、品类销量第一 香甜类 12.9万。
